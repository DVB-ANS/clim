# Chainlink CRE friction log

Developer-experience notes for the Chainlink team, written while building clim. Each entry: what we tried, what happened, what would help. Entries marked *(design phase)* come from reading the docs and templates before writing code. Confirm or correct them during the build.

| # | Area | What we hit | Suggestion | Status |
|---|---|---|---|---|
| 1 | Simulation trust model | `cre workflow simulate` runs a single node, so no real consensus. With `--broadcast` on Sepolia, the report goes through `MockKeystoneForwarder` (0x15fC6ae953E024d975e77382eEeC56A9101f9F88), which skips signature checks: anyone can push a report to a consumer during a demo. | A multi-node local simulation mode, or a mock forwarder that verifies signatures from a local key set. | confirmed on a Sepolia fork (`contracts/test/fork/MockForwarder.fork.t.sol`): `report()` is permissionless and clim's `tx.origin` guard rejects third parties. `simulate --broadcast` sends `report()` from the `CRE_ETH_PRIVATE_KEY` account straight to the mock (tx `0xe57a006e7585984137cb5064d6be6fc7b9353194760178b85a78274c8785fa2c`), so the guard works in simulation; `bots/src/scripts/forge-report.ts` demonstrates it on the live desk |
| 2 | Docs | One docs page says the mock forwarder does not call the consumer's `onReport`, while the mock's source does call it. | Align the docs with the code. | source confirms the mock calls `onReport` (chainlink-evm `contracts/cre/src/dev/MockKeystoneForwarder.sol`, `route`); on a Sepolia fork the deployed mock ("MockKeystoneForwarder 1.0.0") calls `onReport` with `msg.sender` = mock and `tx.origin` = sender; docs page still to re-find |
| 3 | Periodic workflows in simulation | A cron trigger fires once per `simulate` run, so demoing a 30 s cadence needs a shell loop. | A `--watch` / `--loop` mode for cron workflows. | partly addressed in cre v1.37.0: `cre workflow build` + `simulate --wasm` skips recompiling; `--listen` keeps one process alive for HTTP and log triggers, not cron. We loop with `cre/scripts/sim-loop.sh`. |
| 4 | Stateless executions | No state between executions. A rolling metric (15-minute realized volatility) must refetch history every run or read state back from chain. | A small key-value state between executions, or a documented pattern. | design phase |
| 5 | Quotas and latency | Cron minimum interval 30 s, 15 HTTP calls per execution, 250 KB per response, 10 s connection timeout, one HTTP-trigger run per 30 s. End-to-end latency (trigger → consensus → on-chain inclusion) is not documented. | Publish typical end-to-end latency per network. | quotas confirmed; measured in simulation: median 11 s, p90 16 s (tObs → block, 13 reports, `cre/risk-desk/scripts/latency.ts`) |
| 6 | Deploy access | Deploying to a DON needs approval (`cre account access`), with unknown delay during a 36 h hackathon. | A hackathon fast track. | requested on 2026-10-06 at 22:56 SGT with `cre account access` ("Access request submitted successfully!"); `cre whoami`: Not enabled, review pending |
| 7 | Network coverage | Robinhood Chain is testnet-only in the docs (2026-09-18), where our first target DEX is live on mainnet. | Roadmap visibility for new networks. | design phase |
| 8 | Node egress | Builders cannot know where DON nodes run. Some APIs geo-block (Binance returns HTTP 451 to US IPs). | Document egress regions or recommend fallbacks. | design phase |
| 9 | Simulation write status | With `--broadcast`, `WriteReportReply.receiverContractExecutionStatus` is SUCCESS whenever the forwarder tx is mined, but `MockKeystoneForwarder.report` never reverts when the consumer's `onReport` reverts (it emits `ReportProcessed(..., false)`). A rejected report looks like a success to the workflow. Example on Sepolia: tx `0x276dacda91143cb6b8ace8c4d11c8ed8df837620afc01e9fea81c1338a8aa13d`, status 1, `ReportProcessed` false. Workaround in clim: re-read `RiskDesk.state()` after each write. | Decode `ReportProcessed` in the simulator's EVM chain and return REVERTED; say it in the onchain-write guide. | confirmed on Sepolia 2026-10-06: forged tx `0x34ee46a6947d2831fdb3e5a09f831008589efd9cf099f61dca86dc4cdadc53d9` mined with status 1, `ReportProcessed` false, no `RiskReported`, desk unchanged (also on a Sepolia fork in `contracts/test/fork/MockForwarder.fork.t.sol`); the workflow re-reads `RiskDesk.state()` after each write |
| 10 | Dry run | The dry run `eth_call`s the mock forwarder, which swallows consumer reverts, so a dry run cannot tell whether the consumer would accept the report. | Dry-run the consumer call itself, or decode the forwarder's return value. | seen in source (`dryRunWriteReport`); confirmed in plan 02 Task 8: a dry run to the placeholder desk `0x000000000000000000000000000000000000dEaD`, which has no code on Sepolia, returns `txStatus` SUCCESS, no REVERTED receiver status and a zero tx hash (`Write report transaction succeeded: 0x000…000`) |
| 11 | Listen mode docs | The docs say to POST the raw JSON to `http://localhost:2000`. cre-cli v1.37.0 serves `POST /trigger` and reads the payload from `{"input": ...}`. Non-interactive listen also requires `--http-payload` for the first run. | Align "Testing HTTP Triggers in Simulation" with the code. | confirmed 2026-10-06 (cre v1.37.0, plan 02 Task 9): a POST to `http://localhost:2000` (or `/`) answers `404 page not found`; `POST /trigger` with `{"input":{}}` runs the workflow; non-interactive listen without `--http-payload` stops with `✗ --http-payload is required for http-trigger@1.0.0-alpha in non-interactive mode`. The `{"input": ...}` unwrapping is not visible with our workflow (it ignores the payload; a raw body also ran) |
| 12 | Simulation limits | By default the simulator enforces the production HTTP-trigger rate (one run per 30 s, burst 1), so a 30 s POST loop can hit "Trigger rate limited". | Mention it next to `--listen`; `--limits none` lifts it. | confirmed 2026-10-06 (cre v1.37.0, plan 02 Task 9): two POSTs 1 s apart, 33 s after the previous run, both answered 200; the first ran, the second logged `Trigger rate limited, skipping execution trigger=http-trigger@1.0.0-alpha limit=HTTP trigger rate limited: every30s:1`. The 200 (empty body) does not tell the caller that the run was skipped. With `--limits none`, three runs in 7 s |
| 13 | CLI auth | `cre init` and `cre workflow simulate` require `cre login` even for local scaffolding and local runs, while `cre templates list` and `cre workflow build` do not. Teammates without an account cannot run the simulator. | Allow offline dry-run simulation, or say in the install guide that an account is needed before the first simulation. | observed (cre v1.37.0) |
| 14 | SDK exports | `TxStatus` is exported from `@chainlink/cre-sdk`, but the EVM `ReceiverContractExecutionStatus` enum is only reachable through `@chainlink/cre-sdk/pb` (`EVM_PB`). | Export it next to `TxStatus`. | observed (SDK 1.23.0) |
| 15 | Docs | The macOS/Linux install page shows empty version strings ("The recommended version at the time of writing is ****.", expected output "CRE CLI version "). | Fix the version variable on the page. | observed 2026-10-06 |
| 16 | Access request before login | `cre account access` run before `cre login` fails with "credential validation failed: authentication failed: unable to retrieve organization info. Your account may not be fully set up yet, please try again in a few minutes", followed by a network error (`TLS handshake timeout`). It reads like a server-side account problem, not a missing login. | Detect missing credentials first and say "run `cre login`". | observed (cre v1.37.0, 2026-10-06) |
| 17 | Non-interactive access request | `cre account access` only works in a real terminal. From a shell without a TTY (an agent's shell, CI, Claude Code's `!` prefix) it prints "Deployment access is not yet enabled" and then fails with `huh: could not open a new TTY: open /dev/tty: device not configured`. The global `--non-interactive` flag exists, but the command has no flag for the confirmation or the use-case text. | Add flags (for example `--yes --use-case "..."`) so the request can be scripted. | observed (cre v1.37.0); the maintainer submitted it from a regular terminal |
| 18 | Installer output | `install.sh` prints "cre was installed successfully to ~/.cre/cre", but the binary is `~/.cre/bin/cre` (the folder it adds to PATH). It also only edits `~/.zshrc`, so tools whose shell does not re-read it (agent shells) need a symlink on an existing PATH folder. | Print the real path; mention the symlink option for non-interactive shells. | observed (install.sh, 2026-10-06) |
| 19 | Simulator log times | `cre workflow simulate` prints its log timestamps in the machine's local time with a `Z` (UTC) suffix. On a Mac set to Singapore (UTC+8), a run at 15:55:36 UTC printed `2026-10-06T23:55:36Z [SIMULATION] Simulator Initialized`; with `TZ=UTC` the same lines read `15:56:23Z`. Transcripts kept as evidence then disagree with block timestamps and with `date -u` by the UTC offset. | Format the times in UTC, or print the real offset instead of `Z`. | observed (cre v1.37.0, plan 02 Task 8); workaround: run the CLI with `TZ=UTC`, which `cre/scripts/sim-loop.sh` exports (plan 02 Task 9; seen again in listen mode: `00:07:54Z` for 16:07:54 UTC without it) |
| 20 | Simulator paths | From the project root, `cre workflow build ./risk-desk -o ./risk-desk/binary.wasm` writes `cre/risk-desk/binary.wasm`, but `cre workflow simulate risk-desk --wasm ./risk-desk/binary.wasm` from the same directory fails with `✗ validation error` and `--wasm must be a valid existing file: ./risk-desk/binary.wasm`: `simulate` resolves a relative `--wasm` from the workflow folder (`--wasm ./binary.wasm` and an absolute path both work), while `build -o` resolves from the current directory. The error does not say which base it used. | Resolve `--wasm` from the current directory like `-o`, or print the resolved absolute path in the error. | observed (cre v1.37.0, plan 02 Task 9); workaround: `cre/scripts/sim-loop.sh` passes an absolute path |
| 21 | Listen mode shutdown | After SIGTERM (`pkill -f "cre workflow simulate"`), the listen-mode simulator prints `Received interrupt signal, stopping execution` and `Skipping WorkflowEngineV2` and releases port 2000, then stays alive with no output for about 17 s before printing the deploy-access box and exiting. 2 of 3 stops lingered (one for about 17 s, one for more than 3 s before we sent SIGKILL); one exited within a second. | Exit promptly after the interrupt, or print what it is waiting for. | observed (cre v1.37.0, plan 02 Task 9) |
| 22 | Listen mode log order | In `--listen`, the last `[USER LOG]` line of the first run (`DRY RUN: ...`) printed after `✓ Workflow Simulation Result`, `Execution finished signal received` and the next `Listen: ready for next request (run #2)` / `Waiting for HTTP request ...` banner, so a transcript cut at the banner gives that line to the next run. | Flush the workflow's logs before printing the run's result and the next banner. | observed once in 5 listen-mode runs (cre v1.37.0, plan 02 Task 9); in the one-shot `simulate --broadcast` runs of the loop the last `[USER LOG]` line was also lost, never printed, in about 1.7% of runs (7 of 413 on 2026-10-06: the workflow's result was `OK` but `REPORT applied` was missing; one more run returned `NOT_APPLIED` without its `NOT APPLIED` line), each time with `context canceled` at shutdown |
| 23 | Receiver template | `starter-templates/sports-resolution/.../ReceiverTemplate.sol` (cre-templates `d0223f3`) requires `metadata.length == 62`, but KeystoneForwarder and MockKeystoneForwarder pass `rawReport[45:109]` = 64 bytes (workflow id 32, name 10, owner 20, report id 2). As soon as `setExpectedWorkflowId` / `Author` / `Name` is set, every report reverts `InvalidMetadataLength(64, 62)`. Reproduced with a forge test feeding real forwarder metadata. The other templates (circuit-breaker, event-reactor, …) have no length check. | Set `METADATA_LENGTH` to 64 and add a test with real forwarder metadata. Candidate upstream PR. | verified (forge test) |
| 24 | Simulation credentials | `cre workflow simulate` validates the CLI credentials against the CRE API on every run, so a local simulation loop fails whenever that API is slow or unreachable: 5 of 413 runs of our 30 s loop on 2026-10-06 stopped before simulating with `✗ Credential validation failed` and `✗ authentication required: credential validation failed: authentication failed: unable to retrieve organization info. ...` (twice followed by a network error on `https://api.cre.chain.link/graphql`). | Cache the validated credentials for local simulation, or let simulation run offline. | observed (cre v1.37.0, 2026-10-06); `bun run cre-loop` records these runs as `error`, `CRE CLI credential validation failed` |
| 25 | Parallel builds | `cre workflow build` writes a fixed temporary file, `<workflow>/.cre_build_tmp.wasm`. Two builds of the same workflow folder at once (our live and replay loops started in the same second, with different targets) collide, and one fails with `failed to compile workflow: open .../.cre_build_tmp.wasm: no such file or directory`. | Use a unique temporary file per build (or a lock), so builds for several targets can run in parallel. | observed 2026-10-06 (cre v1.37.0); workaround: start the loops a few seconds apart (run-book section 4) |
